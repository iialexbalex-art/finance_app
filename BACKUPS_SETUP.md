## 1. Сначала административная копия, затем SQL

Готовый пакет: `backups-install.zip`. SQL и TXT в нём побайтно одинаковы.
`backups-install/FILES.txt` содержит длину и SHA-256 каждого SQL.

Предварительное сохранение и установка для текущего проекта уже выполнены.
Следующие шаги оставлены как описание процесса, повторно выполнять установку
для подключения сервера не нужно.

1. В **SQL Editor проекта bgyuxibywuxdultxsmiv**, роль **postgres**, выполните
   целиком `PRE_BACKUP_018.sql` (или идентичный TXT). Первая строка:
   `-- PRE_BACKUP_018: read-only administrative copy; download the backup_json result.`
   Последняя: `commit;`. Сохраните результат с единственной колонкой
   `backup_json` через скачивание JSON/CSV, без копирования усечённой ячейки.
   Например, в `.local-backups/database-before-018/export.json`.
   Сценарий сохраняет согласованные данные public/finance_private, структуру,
   функции, политики, триггеры, grants и UUID Auth, без паролей и токенов.
   Финансовые данные являются приватными: не отправляйте файл в чат/репозиторий.
2. В `D:\finance_app` выполните:

   ```powershell
   & .local-backups/worker-venv/Scripts/python.exe tools/verify_admin_backup.py .local-backups/database-before-018/export.json
   ```

   Проверяются целостность, состав, проект и возраст менее часа. Создаются
   проверенная локальная административная копия, checkpoint исходников и
   **`backups-install/INSTALL_BACKUPS_018.sql`**, идентичный TXT и
   `backups-install-verified.zip`. Команда сообщает число строк, первую и
   последнюю строки готового установщика. Эти файлы намеренно не созданы
   заранее из фиктивной копии.
3. Выполните **весь сгенерированный INSTALL_BACKUPS_018.sql** в том же проекте
   как postgres. Установщик блокирует изменения, снова проверяет полный
   отпечаток данных, затем применяет 018 одной транзакцией. Если данные успели
   измениться, повторите шаги 1–2. При ошибке установка откатывается.

`018_BACKUPS_UNGUARDED_DO_NOT_RUN.sql/.txt` — полный исходник миграции для
проверки и тестовой среды. Не выполняйте его непосредственно в рабочей БД
и не обходите проверку параметром `finance.backup_install_verified` вручную.

Альтернатива SQL Editor: защищённо задайте `ADMIN_DATABASE_URL`, установите
совместимые с сервером `pg_dump`/`pg_restore` и выполните:

```powershell
& .local-backups/worker-venv/Scripts/python.exe tools/apply_backup_migration.py --pg-bin PATH_TO_POSTGRES_BIN --apply
```

Этот установщик сам создаёт checkpoint, согласованный custom dump public и
finance_private через экспортированный REPEATABLE READ snapshot, проверяет
дамп и сохраняет блокировки до завершения миграции. Без `--apply` он только
делает копию. Пароль передаётся защищённой переменной окружения, не аргументом
командной строки. Дамп не содержит Auth/Vault secrets.

## 3. Подтверждение копии и расписания

Код `--once`: 0 = created/verified подтверждены; 1 = сбой; 2 = нет заданий/
проверенной копии. JSON отличает новую копию от проверки готовой. Общая
файловая блокировка охватывает HTTP/scheduler/CLI на одном VPS с одним корнем.
Второй cron не устанавливать.

Расписание 23:59 Asia/Qyzylorda (18:59 UTC), poll 30 секунд, UUID дня,
ограниченные повторы, catchup с реальным временем. Статус проверяет heartbeat
и живость потока: остановка/зависание даёт scheduler_active=false/next_run=null,
ошибка S3 не выдаётся за готовую копию. Рабочее расписание пока не включено,
следующего подтверждённого запуска нет.

Хранение: ежедневные/предоперационные 30 дней, месячные 12 месяцев, ручные
до подтверждённого удаления. Последняя готовая и активные export/restore
защищены. Удаляются только SQL-разрешённые snapshot ID, оригиналы сохраняются.
Запас свободного места 5 GiB плюс операция; временные файлы очищаются под
общей блокировкой. Multipart uploads worker не создаёт.

Владелец в приложении переносит локальные шаблоны отчётов в finance_settings,
если серверных ещё нет. Сервер не читает SharedPreferences выключенных
устройств и других офлайн-профилей. После подключения проверить готовую копию
в Настройки → Резервные копии, скачать ZIP и восстановить только в отдельной
тестовой среде. Рабочую БД для проверки не восстанавливать.

## Состав, безопасность и границы

Формат 1 / схема 18 / приложение 1.0.0+1. Снимок владельца содержит все поля
его `spaces`, `wallets`, `wallet_opening_balances`, `categories`, `expenses`,
`incomes`, `transfers`, `finance_settings` (шаблоны и версии assets), историю
за 30 дней и неизменяемые квитанции пяти видов запросов. Сохраняются ID,
валюты, даты, суммы в строках minor без потери int64, курсы/комиссии переводов,
родители, порядок, архивы и изображения. Остатки считаются из первичных данных.
Обновляются revisions и кэши; старые запросы не создают повторные операции.
Источник снимка — единая серверная транзакция под общей блокировкой.

Обычные правки записывают old/new историю атомарно с изменением. Все штатные
RPC и записи затрагиваемых восьми таблиц охвачены серверными триггерами.
Для массовых операций и восстановления необходим готовый полный снимок,
отпечаток которого проверяется непосредственно под блокировкой. При изменении
данных другим клиентом операция отклоняется, необходимо повторить после
обновления. Долгая загрузка файлов не удерживает транзакцию.

Чужие данные, Auth/Vault/ключи/сессии, `space_members`, `wallet_assignments`,
глобальные роли, grants, очередь заданий и технический аудит не импортируются
пользовательским ZIP. Доступ сохраняется по текущим правилам; при удалении
пространства его зависимые разрешения могут удалиться штатно. Локальные черновики
и невыполненная клиентская очередь не являются применёнными финансовыми данными
и не включены. Менеджеру нельзя получить полную копию владельца.

Текущий код использует встроенные assets; проверка Storage в рабочем проекте
не обнаружила buckets. Если позже появятся принадлежащие владельцу объекты
Storage, исполнитель **откажет** в готовой копии до подключения адаптера этих
вложений — пропускать их молча нельзя. Поддержка текущих встроенных оригиналов
реализована и испытана.

Архив не содержит SQL для исполнения; проверяются владелец, формат/схема,
ссылки, дерево, деньги, пути, все хеши. Лимиты: архив и распакованный объём
2 GiB, JSON 64 MiB, отдельный файл 128 MiB, до 10000 элементов. Экспорт
сервером создаётся на временном диске с потоковым копированием оригиналов.
В браузере скачивание большого ZIP требует памяти/места самого браузера.
Импорт проверяется полностью до записи в БД, запись одной транзакцией.

Прямой административный SQL, отключение триггеров, редактирование исходников
в обход checkpoint и произвольные старые скрипты невозможно автоматически
защитить одним Flutter-клиентом. Для миграций используйте подготовленный
установщик. Администратор с postgres остаётся доверенной стороной.

## Возврат программы и новая серверная среда

Перед новой задачей Codex выполняется `python tools/project_checkpoint.py create`
и проверяются все хеши; правило добавлено в AGENTS.md. Объекты исходников/assets
хранятся по SHA-256 в `.local-backups/project-versions`, без дублей. Config с
ключами исключён из обычных версий; защищённая конфигурация хранится отдельно.
Первый приватный ZIP до этой задачи содержит необходимую исходную конфигурацию.

Для возврата исходников:

```powershell
& .local-backups/worker-venv/Scripts/python.exe tools/project_checkpoint.py verify CHECKPOINT_DIRECTORY
& .local-backups/worker-venv/Scripts/python.exe tools/project_checkpoint.py export CHECKPOINT_DIRECTORY EMPTY_DESTINATION
```

Экспортируйте в отдельную пустую папку, настройте защищённую конфигурацию и
соберите оттуда. Возврат кода не откатывает схему/данные. Код этой версии
поддерживает чтение/обычные функции схемы 017 без подключённого API; backups
требуют 018 + API. Старый код до 018 не должен писать кошельки/категории/
остатки напрямую после установки 018: сервер защищённо отклонит такие записи.
Для отката UI используйте совместимый со схемой 018 код, не снимайте grants/
revision-защиту. Поддержка иных форматов/схем требует отдельной проверяемой
миграции; несовместимый ZIP отклоняется.

Удалённого приватного Git/назначения независимых версий проекта в исходном
проекте не было. Нужно отдельно подключить уже разрешённое независимое место
и передать туда проверенные checkpoints/objects, не секреты и финансы.

При утрате Supabase администратор создаёт чистый проект, расширения и схему
по проверенным миграциям/административному дампу, заново настраивает Auth и
доступ. Установки с seed используйте только для чистой тестовой/новой среды,
не повторно поверх рабочей. Auth UUID должны быть сохранены или сопоставлены
явно администратором: пользовательский импорт намеренно не меняет owner_id.
При смене ID требуется отдельное контролируемое преобразование всех ссылок
в административной копии и пересчёт хешей; автоматическое присвоение чужого
владельца браузеру не предоставлено. Затем подключаются worker/диск с оригиналами,
регистрируется версия assets, выбранный самостоятельный ZIP импортируется
в совместимую среду владельцем. Старые задания/ключи не нужны для ZIP.
Полное восстановление серверных Auth/секретов не является функцией пользовательского
архива; их настройка остаётся отдельным административным процессом.
