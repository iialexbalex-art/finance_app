| Попытка | Защита и ожидаемый результат |
| --- | --- |
| Первый вошедший создаёт себе пространство владельца | INSERT требует уже существующее владение; пустая база не назначает владельцев |
| Менеджер пишет `owner` в user_metadata | Политики читают только `auth.uid()` и таблицы, не metadata |
| Менеджер добавляет/обновляет себе role=owner | Нет INSERT/UPDATE GRANT на role, CHECK допускает только manager; INSERT членства требует владельца |
| Менеджер изменяет owner_user_id пространства | Нет UPDATE на этот столбец; UPDATE строки также ограничен её владельцем |
| Владелец назначает владельцем другой UUID через новое пространство | WITH CHECK требует owner_user_id=auth.uid(); передача владения через клиент запрещена |
| Чтение кошелька по угаданному чужому UUID | SELECT RLS проверяет именно владельца либо назначение текущему UID |
| Чтение не назначенного кошелька своего бизнес-пространства | Одного членства недостаточно; требуется wallet_assignments |
| Назначение менеджера в личное пространство | Константа business + составной FK в space_members запрещают даже ошибочную административную вставку |
| Назначение кошелька из другого пространства | Составные FK требуют совпадения space_id у кошелька и участника |
| Перенос кошелька в доступное пространство | Нет UPDATE GRANT на space_id/id; политики UPDATE имеют USING и WITH CHECK |
| Подмена user_id/space_id в назначении через UPDATE/upsert | Нет UPDATE GRANT и UPDATE-политик; только удалить/создать с owner-проверкой |
| Менеджер добавляет себе назначение или другому человеку доступ | INSERT RLS разрешён только владельцу соответствующего пространства |
| Менеджер читает баланс через wallets select * | Денежных столбцов в wallets нет |
| Прямое чтение wallet_opening_balances или JOIN/embedded-select | RLS балансов допускает только владельца; менеджер получает 0 строк |
| Менеджер меняет/удаляет кошелёк или баланс | Политики записи только для владельца; UPDATE/DELETE могут вернуть 0 строк, что не является обходом |
| Чужой владелец читает/меняет другое пространство | Каждая проверка привязана к конкретному space_id и auth.uid(), глобальное владение не даёт доступа |
| Участие отозвано | FK ON DELETE CASCADE убирает назначения; со следующего запроса кошельки невидимы |
| anon / без сессии обращается к таблицам | Все grants отозваны, policies только для authenticated; NULL auth.uid() не проходит проверки |
| TRUNCATE, TRIGGER, REFERENCES через клиент | Все табличные default grants отозваны; обратно выданы только необходимые права |
| Обход RLS через view/RPC | Views/пишущих SECURITY DEFINER RPC нет; helpers возвращают лишь проверку владения текущего UID |
| Подмена search_path helper-функций | search_path пустой, имена квалифицированы, schema CREATE клиентам не выдан |
| Выполнение bootstrap как authenticated | Проверка current_user=postgres и обычные GRANT/RLS; скрипт не SECURITY DEFINER |
| Неправильный или отсутствующий UUID bootstrap | Проверка UUID и точного auth.users.id; транзакция откатывается |
| Повтор bootstrap | Блокируется выбранная auth.users строка, существующие пространства владельца сохраняются |

## Почему нет рекурсии RLS

`spaces → space_members → owns_space()`; helper читает spaces от имени
создателя postgres и возвращает boolean, не применяя повторно RLS владельца
таблицы. `wallets → wallet_assignments → owns_space()` и
`wallet_opening_balances → wallets` также завершаются в этом helper.
Helpers имеют STABLE, не выполняют записей и не принимают user_id.
EXECUTE от PUBLIC/anon отозван внутри той же транзакции, что создаёт функции.
Владелец функций задан ролью выполнения миграции, которая проверяется как postgres.

## Границы проверки

- Supabase подписывает сессию; end-user не может подменять `auth.uid()` через
  обычный API. SQL Editor postgres намеренно может имитировать UID в тестах.
  Доступ администратора БД сам по себе обходит пользовательский RLS.
- RLS ограничивает будущие запросы. Уже прочитанные клиентом данные невозможно
  «отозвать» с устройства пользователя.
- Роли относительно пространства: один и тот же UUID может быть владельцем
  своего пространства и менеджером чужого; владение своим не расширяет
  прав на чужое.
- Текущие политики не разрешают запись расходов: таблицы операций нет.
  Категории, авторство, права на исправление и суммы операций проверяются
  отдельной будущей миграцией, а не этой.
- Любые последующие views, RPC, grants и permissive RLS-политики требуют
  повторной проверки: новая permissive policy объединяется с прежними через OR.
- Перед выпуском нужны выполнение тестового SQL на отдельной базе/ветке
  и проверки реальными Supabase Auth сессиями, включая Data API joins.
# Дополнение: категории (30.09.2026)

Подготовлены `migrations/202609300002_categories.sql` и
`tests/02_categories_access.sql`; SQL НЕ выполнялся. Статическая проверка:
владелец ограничен своим пространством, менеджер — SELECT расходов через
собственное участие в бизнес-пространстве. Пользовательские metadata не участвуют.
Новая таблица явно сбрасывает default grants; INSERT/UPDATE разрешают только
необходимые колонки. Нет DELETE и изменения структуры категории. Проверка
родителя закреплена составным FK на вычисляемый признак корня; пространство,
тип, отсутствие циклов и третьего уровня защищены независимо от интерфейса.
Новых SECURITY DEFINER функций нет. FK пространства RESTRICT сохраняет категории
при попытке удаления пространства. Архив родителя логически распространяется
на детей; будущая таблица операций должна проверять оба флага на сервере.
