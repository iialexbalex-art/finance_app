## Порядок

1. Сначала в отдельном тестовом проекте/ветке со схемой 003 примените миграцию
   004 целиком в SQL Editor как **postgres**. Она выполняется одной транзакцией.
   При ошибке остановитесь, при необходимости `rollback;`; не обходите ограничения.
2. Там же запустите целиком [04_category_tree.sql](tests/04_category_tree.sql).
   UUID не заменять. Тест создаёт временные по времени транзакции fixtures и
   откатывает их. Ожидается NOTICE `PASS: three-level tree and access...` без ошибок.
3. Для проверки сохранности существующих данных есть альтернативный способ
   шага 1: **до применения 004**, в одном соединении psql тестового проекта со
   схемой 003 и существующими двухуровневыми категориями, выполните
   [04_migration_preservation.psql](tests/04_migration_preservation.psql).
   Этот скрипт сам применяет 004 и сравнивает все старые ID, имена, связи,
   собственные архивные флаги и даты создания. После него НЕ применяйте 004 повторно.
   Он предназначен для psql, не SQL Editor. Затем выполните шаг 2.
4. Выполните [конкурентные сценарии](tests/04_category_tree_concurrency.md)
   в двух независимых постоянных сессиях тестовой базы: два переноса, цикл,
   создание потомка одновременно с переносом, архивирование предка, старый snapshot.
5. После успешной проверки в `finance-app-dev` выполните **только миграцию 004**,
   один раз как postgres. 001–003 и bootstrap повторять не нужно.
6. Перезапустите актуальную версию (старые вкладки могут показывать прежний код):

   ```powershell
   cd D:\finance_app
   flutter run -d chrome --dart-define-from-file=config/local.json
   ```

SQL-тест **04 заменяет 02 и 03** для текущей схемы. Старые файлы сохранены для
соответствующих старых схем. Тест **01** по пространствам/кошелькам остаётся актуальным.

## Что проверять вручную

«Категории» → выбрать пространство/тип → «Добавить категорию» → поле
«Родительская категория». Создать «Ежедневные → Еда → Продукты», проверить F5.
Варианты показывают полный путь. «Добавить подкатегорию» предвыбирает нужную запись.
У «Продуктов» объясняется запрет четвёртого уровня.

Перенести ветвь «Еда → Продукты» к другому корню и в корень; проверить ID, имена
и архивные флаги всех потомков. Родитель, который создаёт четвёртый уровень,
не предлагается. Архивировать «Ежедневные»: и «Еда», и «Продукты» показываются
архивными по предку, собственные флаги не меняются. Старый родитель виден в форме,
но архивные цепочки не предлагаются как новые родители.

Проверить менеджера, ошибки сети, повторное сохранение, переключение контекста
во время запроса и параллельные изменения. Обычная сессия менеджера читает только
расходы своего бизнеса, без возможности менять дерево.

## Почему конкуренция защищена

Составной FK сохраняет совпадение space_id/kind в каждой связи. После каждой
записи база обходит цепочки всех категорий, отклоняя циклы и глубину больше трёх:
поэтому проверяются все потомки переносимой ветви. Перенос меняет parent_id одной
существующей записи атомарно; дочерние записи не пересоздаются и не обновляются.
Для нового parent_id проверяется архив по всей цепочке, включая дедушку.

Одного обхода недостаточно: BEFORE STATEMENT триггер делает реальный UPDATE
единственной строки `finance_private.category_tree_guard`. Все записи категорий
ждут завершения предыдущей транзакции. При READ COMMITTED VOLATILE-функции
получают свежие snapshots после ожидания; при RR/SERIALIZABLE устаревшая
транзакция не может обновить изменённую guard-строку и получает ошибку сериализации.
Это распространяется и на архивирование, создание потомков и многострочные UPDATE.
Архивирование ПОСЛЕ успешно завершённого переноса разрешено: архивируется уже
существующая ветвь. Ошибки 40001/40P01 требуют обновления данных/повтора транзакции.

Служебные функции SECURITY DEFINER выполняют только фиксированные операции
блокировки/валидации, имеют пустой search_path, не принимают пользовательские
аргументы, не возвращают чужие данные и недоступны через клиентский EXECUTE.
У guard-таблицы нет клиентских прав. RLS и GRANT категорий не расширены:
изменение id/space_id/kind по-прежнему запрещено; менеджер писать не может.

Компромисс: запись категорий сериализуется также между разными пространствами,
а валидация обходит справочник. Для текущего небольшого справочника это простая
проверяемая защита; при росте нагрузки потребуется отдельная оптимизация.
Официальные основания: [снимки VOLATILE-функций](https://www.postgresql.org/docs/17/xfunc-volatility.html),
[проверки согласованности и необходимость UPDATE](https://www.postgresql.org/docs/15/applevel-consistency.html).
