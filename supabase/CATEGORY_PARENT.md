4. В рабочем `finance-app-dev` примените только миграцию **003**, один раз,


## Что проверить в приложении

«Категории» → нужное пространство/тип → у «Еда» **Редактировать** →
**Родительская категория** → «Ежедневные» → **Сохранить**.
Повторить с другим родителем и с «Без родительской категории», обновить F5.
ID и собственный `is_archived` записи должны остаться прежними.
Архивный текущий родитель отображается, но не предлагается для нового назначения.
Категорию с детьми нельзя вложить; сначала перенесите детей. Проверьте менеджера,
повторное сохранение, сетевые ошибки, изменение родителя из двух вкладок.
PATCH сравнивает прежние name/is_archived/parent_id (включая NULL), поэтому
отличающаяся параллельная правка не должна незаметно перезаписываться.

## Конкурентная проверка — подготовлена, не запускалась

Нужны **две независимые SQL-сессии** одного отдельного тестового проекта
(например, два подключения psql). Не полагайтесь на сохранение транзакции между
запусками SQL Editor через пул соединений. В тестовом проекте заранее создайте
владельцем две активные корневые категории одного пространства/типа без детей.
Запишите их UUID как `CHILD_UUID` и `PARENT_UUID`, UUID владельца как `OWNER_UUID`.
Подставьте эти три значения в команды; новые ключи/пароли приложению не нужны.

В сессии A:

```sql
begin;
set local role authenticated;
select set_config('request.jwt.claim.sub', 'OWNER_UUID', true);
update public.categories set is_archived = true where id = 'PARENT_UUID';
-- Оставить транзакцию открытой.
```

В сессии B:

```sql
begin;
set local role authenticated;
select set_config('request.jwt.claim.sub', 'OWNER_UUID', true);
update public.categories set parent_id = 'PARENT_UUID' where id = 'CHILD_UUID';
-- Запрос должен ждать A.
```

В A выполнить `commit;`. B должна завершиться ошибкой `23514` об архивном родителе
(при более строгой изоляции допустима ошибка сериализации). В B выполнить
`rollback;`. У CHILD_UUID родитель остался NULL.

Затем восстановите активность тестового родителя как владелец. Повторите в обратном
порядке: B выполняет перенос без COMMIT; A пытается архивировать и ждёт. После
COMMIT B архивирование A разрешено: это последовательное архивирование уже
существующего поддерева, обе записи сохраняются. Откатите A через ROLLBACK.

Отдельно проверьте конкуренцию вложения родителя с добавлением ему ребёнка:
создайте третий активный корень OTHER_UUID. Перед каждым порядком выполнения
верните CHILD_UUID в корень (`parent_id=NULL`) и убедитесь, что
PARENT_UUID/OTHER_UUID — активные корни без детей. B переносит CHILD_UUID в PARENT_UUID
без COMMIT; A пробует вложить PARENT_UUID в OTHER_UUID. После COMMIT B запрос A
обязан завершиться ошибкой FK (не третьим уровнем). В обратном порядке перенос
ребёнка должен быть отклонён. При взаимных переносах допустим deadlock с откатом
одной транзакции; цикл не должен сохраниться. После каждой ошибки — ROLLBACK.
Тестовые категории можно архивировать; для этих проверок не использовать рабочие данные.

## Серверная защита

Добавляется только UPDATE(parent_id) для authenticated. Существующая RLS всё равно
разрешает UPDATE только владельцу пространства. UPDATE(space_id/kind/id), DELETE,
TRUNCATE не предоставляются. Составной FK схемы 002 продолжает защищать тип,
пространство, два уровня и категории с детьми.

Новый SECURITY INVOKER триггер с пустым search_path проверяет нового родителя
для INSERT и изменённого parent_id. SELECT FOR SHARE удерживает строку до конца
транзакции, конфликтуя с архивированием/переносом родителя. Неизменённый архивный
родитель не мешает переименованию. Триггеру не предоставлен клиентский EXECUTE;
административных RPC нет. Основание выбора блокировки:
[PostgreSQL: Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html).

SQL-тесты и конкурентные сценарии не запускались агентом. Flutter-проверки
используют моки; они не заменяют выполнение SQL и ручную проверку Supabase.
