# Конкурентные проверки расходов — НЕ ЗАПУЩЕНЫ

Только отдельный тестовый проект после 001–005. Нужны две постоянные
независимые SQL-сессии A/B (например, psql). SQL Editor не гарантирует
сохранения соединения между нажатиями Run. Ниже fixtures фиксируются, чтобы
их видели обе сессии. Не использовать рабочие UUID и рабочий проект.

## Подготовка как postgres один раз

```sql
begin;
insert into auth.users(id) values
 ('00000000-0000-4000-8000-000000000071'),
 ('00000000-0000-4000-8000-000000000072');
insert into public.spaces(id,owner_user_id,kind,name) values
 ('10000000-0000-4000-8000-000000000071','00000000-0000-4000-8000-000000000071','business','Expense race fixtures');
insert into public.space_members(space_id,user_id) values
 ('10000000-0000-4000-8000-000000000071','00000000-0000-4000-8000-000000000072');
insert into public.wallets(id,space_id,name,wallet_group,currency) values
 ('20000000-0000-4000-8000-000000000071','10000000-0000-4000-8000-000000000071','Race wallet','cash','RUB');
insert into public.wallet_assignments(space_id,wallet_id,user_id) values
 ('10000000-0000-4000-8000-000000000071','20000000-0000-4000-8000-000000000071','00000000-0000-4000-8000-000000000072');
insert into public.categories(id,space_id,kind,name) values
 ('30000000-0000-4000-8000-000000000071','10000000-0000-4000-8000-000000000071','expense','Parent');
```

Сессия A — владелец; выполнить один раз вне транзакции:

```sql
set role authenticated;
select set_config('request.jwt.claim.sub','00000000-0000-4000-8000-000000000071',false);
```

Сессия B — менеджер; выполнить один раз вне транзакции:

```sql
set role authenticated;
select set_config('request.jwt.claim.sub','00000000-0000-4000-8000-000000000072',false);
```

## 1. Архивирование предка успевает первым

A:

```sql
begin;
update public.categories set is_archived=true where id='30000000-0000-4000-8000-000000000071';
-- Пока НЕ COMMIT.
```

B:

```sql
begin;
set local lock_timeout='60s';
select public.create_expense(
 '40000000-0000-4000-8000-000000000071',
 '10000000-0000-4000-8000-000000000071',
 '20000000-0000-4000-8000-000000000071',
 '30000000-0000-4000-8000-000000000072','100',date '2026-09-30','race');
```

B должен ждать. В A выполнить `commit;`. B должен получить **P1001**;
выполнить в B `rollback;`. В A история этого пространства пуста.
В A восстановить `is_archived=false` у родителя отдельным UPDATE.

## 2. Отзыв назначения или участия успевает первым

Повторить сценарий 1, заменив UPDATE в A на:

```sql
delete from public.wallet_assignments where wallet_id='20000000-0000-4000-8000-000000000071'
 and user_id='00000000-0000-4000-8000-000000000072';
```

После COMMIT A ожидается **42501**, не расход. B делает ROLLBACK.
Восстановить назначение в A тем же INSERT, что в подготовке.
Повторить с `delete from public.space_members where
space_id='10000000-0000-4000-8000-000000000071' and
user_id='00000000-0000-4000-8000-000000000072';`.
Ожидается 42501. Восстановить участие и назначение в A.

## 3. Расход успевает первым

В B выполнить `begin;` и тот же вызов `create_expense` из сценария 1.
Не фиксировать. В A начать транзакцию и удалить назначение как в сценарии 2.
A должен ждать. В B выполнить `commit;`, затем в A `commit;`.

В A расход существует ровно один. В B следующий SELECT из `public.expenses`
не возвращает его, повтор RPC получает 42501, RPC остатка также получает 42501.
Если ошибка была внутри BEGIN, завершить `rollback;`.
Восстановить назначение в A. Аналогично повторить с архивированием родителя:
расход до архива допустим, последующие новые UUID запрещены P1001.
Старый UUID с теми же параметрами возвращает старый ID при сохранённом доступе.
Затем восстановить архивный флаг в A.

## 4. Два одновременных одинаковых запроса

Для этого сценария A временно становится тем же менеджером, что B:

```sql
select set_config('request.jwt.claim.sub','00000000-0000-4000-8000-000000000072',false);
```

В обеих сессиях BEGIN и вызов из сценария 1, но request_id заканчивается
на **000000000074**. В A выполнить вызов первым и не фиксировать. B должен
ждать. COMMIT A → вызов B возвращает **тот же UUID** → COMMIT B.

```sql
select count(*),count(distinct id) from public.expenses
where request_id='40000000-0000-4000-8000-000000000074';
-- Оба значения должны быть 1.
```

Повтор с тем же request_id, но суммой `'101'` должен дать P1002.
Вернуть в A UUID владельца из настройки сессии A.

## 5. Старый snapshot REPEATABLE READ

B: `begin isolation level repeatable read;` и SELECT доступных категорий,
чтобы получить snapshot. A: BEGIN, архивирование родителя, COMMIT.
B: вызов RPC с новым request_id, заканчивающимся на **000000000075**.
Ожидается **40001** при обновлении guard, расход не создаётся. B: ROLLBACK.
Новый запрос в новой транзакции уже видит архив и получает P1001.
Повторить с отзывом назначения: старый snapshot →40001, новая транзакция →42501.
Так же проверить SERIALIZABLE. При deadlock ожидается 40P01 с полным откатом,
после повтора результат должен соответствовать уже зафиксированным правам.

## Очистка fixtures как postgres после завершения обеих транзакций

Только UUID этого теста. Выполнять после всех проверок в тестовом проекте.

```sql
reset role;
begin;
delete from public.expenses where space_id='10000000-0000-4000-8000-000000000071';
delete from public.categories where id='30000000-0000-4000-8000-000000000072';
delete from public.categories where id='30000000-0000-4000-8000-000000000071';
delete from public.spaces where id='10000000-0000-4000-8000-000000000071';
delete from auth.users where id in
 ('00000000-0000-4000-8000-000000000071','00000000-0000-4000-8000-000000000072');
commit;
```

Записать результаты каждого порядка гонки. Однопоточный тест 05 не подтверждает
эти проверки, и наличие данной инструкции не означает, что они уже выполнены.
