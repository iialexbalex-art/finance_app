# Конкурентная проверка 006 (подготовлено, не запускалось)

Использовать отдельный тестовый проект с 001–006 и две независимые SQL-сессии.
Тест 06 проверяет устаревшие версии последовательно; реальное ожидание блокировки
проверяется здесь. Не использовать реальные денежные записи.

Подготовить владельца, пространство, два кошелька одной валюты, активную категорию
и один тестовый расход через `create_expense`. Зафиксировать подготовку. В обеих
сессиях сохранить одинаковые ID расхода и его `revision` до начала транзакций.
Вызовы выполнять с `set local role authenticated` и
`select set_config('request.jwt.claim.sub','UUID_ВЛАДЕЛЬЦА',true)` после `begin`.

Сигнатура запроса (подставить UUID и валюту тестовых данных):

```sql
select public.edit_expense(
  'UUID_ЗАПРОСА', 'UUID_ПРОСТРАНСТВА', 'UUID_РАСХОДА', 'ИСХОДНАЯ_REVISION',
  'UUID_КОШЕЛЬКА', 'UUID_КАТЕГОРИИ', '30000', date '2030-01-01',
  'concurrency test', 'RUB', 2
);
```

1. Сессия A: `begin`, установить владельца/роль, выполнить запрос, **не commit**.
2. Сессия B: `begin`, установить владельца/роль, вызвать запрос с той же исходной
   версией, но другим UUID запроса и суммой. B должна ждать A.
3. A: `commit`. B получает `P1003`; выполнить `rollback`. Проверить: ID, автор,
   created_at и пространство прежние, сумма A; нет строки/квитанции запроса B.
4. Повторить с совершенно одинаковыми параметрами и UUID в A/B. После commit A
   B возвращает тот же ID; версия меняется только один раз, квитанция одна.
5. Повторить с одинаковым UUID, но разными суммами: B получает `P1002`.
6. Выполнить ещё одну успешную правку с новой версией. Повторить самый первый
   успешный запрос: возвращается ID, последняя правка не откатывается.

Для каждого сценария брать свежую `revision` и новые UUID запросов.
Проверять оба остатка одним SQL-запросом в третьей сессии:

```sql
select public.wallet_expense_balance('UUID_СТАРОГО_КОШЕЛЬКА'),
       public.wallet_expense_balance('UUID_НОВОГО_КОШЕЛЬКА');
```

До commit A оба результата старые; после commit оба новые. Нет промежуточного
состояния, в котором расход списан из обоих кошельков либо ни из одного.

Отдельно проверить архивирование предка новой категории и смену владельца
пространства во время правки. Если правка захватила guard первой, изменение
справочника/доступа ждёт её commit. Если архив/смена владельца произошли первыми,
правка отклоняется (`P1001`/`42501`). Повтор после утраты владения тоже запрещён.
Прежнюю архивную категорию разрешено оставлять при правке существующего расхода.

Повторить конкуренцию в `repeatable read`: перед commit A зафиксировать старый
snapshot B чтением таблицы. Ожидается `40001`, затем rollback и новая транзакция
с тем же UUID запроса; она либо подтверждает повтор, либо возвращает `P1003`.
`40P01` также требует новой транзакции с тем же UUID. После проверки удалить
тестовый проект/ветку обычным административным порядком.
