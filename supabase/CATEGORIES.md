## SQL

1. Рекомендуется сначала проверить в отдельном тестовом проекте/ветке Supabase.
   Там должна быть применена исходная `202609300001_spaces_wallets.sql`.
   В SQL Editor как **postgres** выполните целиком
   [202609300002_categories.sql](migrations/202609300002_categories.sql).
2. В этом же изолированном проекте выполните целиком
   [02_categories_access.sql](tests/02_categories_access.sql).
   UUID не заменяйте: пользователи и данные фиктивные. Тест заканчивается
   `ROLLBACK`, а перед ним выводит NOTICE `PASS: category boundaries...`.
   Любое исключение `FAIL` означает провал. После ошибки при необходимости
   выполните `rollback;` отдельно. Повторите там же прежний
   [01_access_boundaries.sql](tests/01_access_boundaries.sql) для регрессии.
3. После успешной проверки в `finance-app-dev` выполните **только новую**
   `202609300002_categories.sql`, целиком, один раз, роль postgres.
   Прежнюю миграцию и bootstrap повторять не нужно. Новых UUID, ключей и примеров
   категорий добавлять не требуется. При SQL-ошибке остановитесь и сохраните текст.
4. Перезапустите приложение из папки проекта:

   ```powershell
   cd D:\finance_app
   flutter run -d chrome --dart-define-from-file=config/local.json
   ```

В текущем сеансе агента SQL-миграция и SQL-тесты **не запускались** ни локально,
ни в Supabase. Подготовленные SQL-тесты не являются подтверждением выполненной
проверки RLS. Статус Flutter-проверок указан в [PLAN.md](../PLAN.md).

## Интерфейс и ручная проверка после SQL

- Войдите владельцем → «Категории» → выберите пространство → «Расходы»/«Доходы».
  Создайте категорию, под ней — подкатегорию. Проверьте переименование и F5.
- Переключите пространство и тип: категории не должны смешиваться; третий уровень
  недоступен. Проверьте длинное название и работу на узком экране.
- «Архивировать» открывает подтверждение с кнопкой «Сохранить». Записи остаются
  видимыми с пометкой архива. Архив родителя распространяется на всё поддерево
  логически: у дочерних записей `is_archived` принудительно не меняется.
  Будущие операции обязаны проверять и свой флаг, и флаг родителя на сервере.
  Восстановление из архива и перенос категорий сейчас не входят в интерфейс.
- Под менеджером своего бизнеса видны только расходы, включая архивные для истории;
  нет создания/редактирования, личных категорий и доходов. Проверьте реальные
  запросы с обычной сессией менеджера и отзыв участия владельцем.
- Проверьте сбой сети, повторное нажатие сохранения, смену типа/пространства и
  выход во время запроса. При неопределённом результате создания сначала обновите
  список: запрос мог сохраниться. После параллельного переименования/архивирования
  устаревшая правка должна завершиться ошибкой с предложением обновления.

## Защита схемы

Одна новая таблица `public.categories`. RLS: владелец своего пространства читает,
создаёт, изменяет; участник-менеджер читает только `expense` своего бизнес-пространства.
Принадлежность бизнесу гарантируется существующим FK в `space_members`.
Чужой владелец, посторонний и anon не получают доступа. Metadata роли не используется.

GRANT: SELECT, INSERT только `space_id,kind,name,parent_id`, UPDATE только
`name,is_archived`. DELETE, TRUNCATE, REFERENCES, TRIGGER и изменение id/родителя/
пространства/типа не предоставляются. Удаление пространства с категориями
блокируется FK RESTRICT, чтобы сохранить историю. Старые миграции и права не менялись.

Дерево ограничено составным FK `(space_id,kind,parent_id,true)` на
`(space_id,kind,id,is_root)`, где признаки вычисляются базой. Родителем может быть
только корень того же типа и пространства. Это исключает циклы и третий уровень
без триггерных гонок и без новых SECURITY DEFINER функций.

При проверке использованы официальные описания
[RLS и GRANT Supabase](https://supabase.com/docs/guides/api/securing-your-api) и
[вычисляемых колонок PostgreSQL](https://www.postgresql.org/docs/current/ddl-generated-columns.html).
