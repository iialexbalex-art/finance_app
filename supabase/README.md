## Порядок действий в Supabase

1. Откройте нужный проект Supabase. В **Authentication → Users** найдите свою
   учётную запись по email, откройте её и скопируйте полный **User UID / ID**
   вида `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`. Нужен UUID пользователя,
   а не Project ID, email или ключ API. Сверьте email именно той записи,
   которой вы уже входили в приложение. UUID присылать в чат не требуется.
2. Откройте **SQL Editor → New query**, выберите роль **postgres**.
   Скопируйте **весь** файл
   [миграции](migrations/202609300001_spaces_wallets.sql) и нажмите **Run**.
   Она создаёт таблицы, ограничения, RLS и GRANT одной транзакцией.
   При успехе обычно выводится `Success. No rows returned`.
   Миграцию выполняют один раз: не добавляйте `IF NOT EXISTS` и не обходите
   ошибку совпадения имён, так можно принять несовместимую старую схему за новую.
3. Создайте ещё один запрос в SQL Editor. Вставьте целиком
   [02_create_owner_spaces.sql](bootstrap/02_create_owner_spaces.sql).
   Только в строке `supplied_uuid text := 'REPLACE_WITH_EXACT_AUTH_USER_UUID';`
   замените содержимое кавычек скопированным UUID. Ещё раз сверьте учётную
   запись. Нажмите **Run** под ролью **postgres**.
4. Скрипт создаст «Личные финансы» (`personal`) и «Бизнес» (`business`).
   В выведенных строках `owner_user_id` должен точно совпасть с вашим UUID.
   Неверный формат или несуществующий UUID прервёт транзакцию без изменений.
   Повторный запуск bootstrap с тем же UUID не создаёт дополнительные
   пространства того же типа и не переписывает существующие.

Если SQL Editor показывает ошибку, остановитесь и сохраните её текст.
Если редактор сообщает об уже прерванной транзакции, выполните `rollback;`
отдельным запросом. Не продолжайте к bootstrap, пока миграция не завершилась.
Если ID существует, но принадлежит другому человеку, скрипт не может угадать
ошибку: именно поэтому нужно сверить email и UUID до запуска.

`postgres` в SQL Editor — административная роль. Успешное чтение под ней
**не проверяет** ограничения менеджера: RLS оценивается для клиентской роли
`authenticated` и UUID из подписанной Supabase Auth сессии.
Пароль БД, service_role и secret key для этих действий не нужны.

## Какие объекты создаются

| Таблица | Назначение |
| --- | --- |
| `spaces` | Личные/бизнес-пространства; единственный источник владения — `owner_user_id` |
| `space_members` | Приглашённые участники: только роль `manager` и только бизнес-пространства |
| `wallets` | Название, группа, валюта и её масштаб; денежных сумм нет |
| `wallet_assignments` | Какие конкретно кошельки назначены участнику пространства |
| `wallet_opening_balances` | Начальные балансы, доступные только владельцу |

Последние две таблицы нужны уже сейчас для точного назначения кошельков и
отделения скрытых денег от доступных менеджеру реквизитов. Таблиц операций,
доходов, переводов, категорий, импорта и будущих отчётов нет.

Владелец не дублируется в `space_members`: он определяется внешним ключом
`spaces.owner_user_id → auth.users.id`. Роль участника нельзя изменить на
`owner`, даже владельцу. Первичное назначение владельца делает только
административный bootstrap по явно введённому UUID. Триггера «первый вошедший
становится владельцем» нет. Владение одним пространством не даёт доступа
к чужим пространствам.

Уже назначенный владелец может создавать дополнительные пространства
**только для себя**, переименовывать и удалять свои пространства, управлять
кошельками и назначать/отзывать менеджеров. Клиент не может менять владельца
или тип пространства. Если владелец удалит все свои пространства, первичное
право создавать их потребуется восстановить через административный bootstrap.
Удаление пространства каскадно удаляет его кошельки и назначения: применять
его следует только как намеренное удаление всего пространства.

## Доступ из приложения / Data API

| Действие | Владелец своего пространства | Назначенный менеджер | Посторонний / без входа |
| --- | --- | --- | --- |
| Читать личное пространство и его кошельки | Да | Нет | Нет |
| Читать бизнес-пространство | Да | Только пространство своего участия | Нет |
| Читать реквизиты бизнес-кошельков | Все свои | Только явно назначенные | Нет |
| Читать начальные балансы | Свои | Нет, даже `select *` и через join | Нет |
| Менять реквизиты/балансы кошельков | Свои | Нет | Нет |
| Назначать/отзывать менеджеров и кошельки | В своих бизнес-пространствах | Нет | Нет |
| Читать участников/назначения | Своих пространств | Только собственные строки | Нет |
| Самостоятельно стать владельцем | Уже владелец может создать своё пространство | Нет | Нет |

Назначение состоит из двух записей: владелец добавляет существующий Auth UUID
в `space_members(space_id, user_id)`, затем назначает конкретный кошелёк через
`wallet_assignments(space_id, wallet_id, user_id)`. До второго шага менеджер
не видит ни одного кошелька. Роль `manager` проставляется по умолчанию.
Отзыв участия удаляет назначения каскадно; следующий запрос теряет доступ.
Интерфейс назначения доступов в этом этапе не создаётся.

**Расходы пока добавлять нельзя никому:** таблицы операций ещё нет.
Этот этап только закладывает бизнес-участие и назначение кошельков.
При создании операций потребуются отдельные RLS/GRANT: менеджеру только
расход, свой автор, назначенный бизнес-кошелёк, разрешённая категория;
доходы/переводы/чужие записи запрещены. Эти ограничения ещё не реализованы
и не должны считаться проверенными до следующего этапа.

## Деньги и неизменяемые поля

`amount_minor` — PostgreSQL `bigint`, целое число минимальных единиц.
`currency_scale=2`: `12345` означает `123.45`; для RUB/KZT масштаб 2.
Масштаб 0–4 задаётся при создании кошелька. `currency` — три заглавные
латинские буквы; пока это проверка формата, а не справочник всех ISO-валют.
Не преобразовывать суммы в `float`/`double`. Flutter теперь читает сумму через
`amount_minor::text` и отправляет JSON-строкой; разбор и форматирование выполняются
через BigInt. INSERT создаёт строку, PATCH изменяет только amount_minor.
Дополнительная миграция и изменение прав не требуются.

Валюта, масштаб, `space_id` и UUID кошелька не изменяются через клиент:
смена валюты/масштаба не должна переинтерпретировать существующие деньги.
Строка начального баланса создаётся владельцем отдельно; отсутствие строки
означает «начальный баланс не задан». Текущие остатки не хранятся и не считаются.
Связывание карты с банковским счётом и защита от двойного учёта — следующий
этап модели операций; здесь группа `card` является только классификацией.

## Проверка защиты

Проведён статический разбор политик, GRANT, внешних ключей и путей повышения прав.
Сценарии и выводы записаны в [SECURITY_REVIEW.md](SECURITY_REVIEW.md).
При подготовке SQL агент не запускал миграцию и проверки под ролями.
Позднее пользователь подтвердил их успешное ручное выполнение в `finance-app-dev`.
Проверка реальными сессиями через интерфейс и Data API остаётся отдельным шагом.

Для воспроизводимой проверки подготовлен
[тестовый SQL](tests/01_access_boundaries.sql). Он предназначен для отдельного
тестового проекта/ветки **после той же миграции**, запускается целиком под
`postgres`, создаёт фиктивные Auth UUID внутри транзакции, проверяет действия
под `authenticated`/`anon` и заканчивается `ROLLBACK`. Bootstrap с реальным
UUID ему не нужен. Этот дополнительный тест сейчас выполнять не обязательно;
перед подключением данных к интерфейсу его нужно выполнить и исправить
любые ошибки. После этого отдельно проверяются реальные запросы Data API
из сессий владельца и менеджера.

Схему `finance_private` не добавлять в Exposed schemas Data API.
В ней только две закрытые для `anon` read-only функции проверок владельца;
они не принимают произвольный UUID пользователя и не возвращают данные.

[доступ к столбцам](https://supabase.com/docs/guides/database/postgres/column-level-security),
[безопасный SECURITY DEFINER](https://www.postgresql.org/docs/current/sql-createfunction.html),
[Authentication → Users](https://supabase.com/docs/guides/auth/managing-user-data).
